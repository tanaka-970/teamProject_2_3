# LNK2001 未解決シンボル 修正報告

作成日: 2026-07-31
症状: `SceneSerializer::Save` / `SceneSerializer::Load`（SceneDocument 版）が未解決。`3dgp.exe` が生成されない。

---

## 1. 未解決シンボルが発生した直接原因

**同名の `.cpp` が 2 つ存在し、両方が同じ `.obj` へ出力されて上書きし合っていた。**

```
RePlayEngine\Scene\SceneSerializer.cpp               ← 旧 SceneDocument 版
RePlayEngine\Scene\Serialization\SceneSerializer.cpp ← 新 v7 SceneData 版
```

`3dgp.vcxproj` には `<IntDir>` も `<ObjectFileName>` も設定されておらず、MSVC は既定で
**全 `.obj` を `$(Platform)\$(Configuration)\` 直下へフラットに出力する**。
その結果、どちらも `x64\Debug\SceneSerializer.obj` になり、後にコンパイルされた方が
先の方を上書きした。

上書きで消えたのが旧 `SceneSerializer::Save` / `Load` の定義だったため、
それを呼んでいる 2 つの翻訳単位からリンク時に未解決となった。

```
framework_scene_document.obj  → SceneSerializer::Save / Load を参照
PrefabSerializer.obj          → SceneSerializer::Save / Load を参照
                                  ↓
                   定義を含む SceneSerializer.obj が上書きされて消失
                                  ↓
                   LNK2001 × 2 → LNK1120 → 3dgp.exe 生成されず
```

**私の見落としでした。** 新しい `SceneSerializer.cpp` を追加したとき、ファイル名の衝突が
MSVC のオブジェクト出力レベルで問題になることを確認していませんでした。
Linux 側の検証では `-o` で出力名を明示していたため再現しませんでした。

補足: 検証環境でこの修正を確認する際、私自身がまったく同じミス（同じ `.cpp` を 2 つの
`.o` 名でコンパイルしてリンク）を踏み、`multiple definition` エラーを出しました。
症状は逆（重複定義）ですが、原因は同じ「オブジェクト名の管理不足」です。

## 3. 各参照をどう修正したか

### 3-1. 旧 SceneSerializer → `LegacySceneDocumentSerializer` へ分離

```
RePlayEngine/Scene/SceneSerializer.h    → 削除
RePlayEngine/Scene/SceneSerializer.cpp  → 削除
RePlayEngine/Scene/Legacy/LegacySceneDocumentSerializer.h   (新規)
RePlayEngine/Scene/Legacy/LegacySceneDocumentSerializer.cpp (新規・中身は旧実装を移設)
```

新旧を混同させないために 4 段階で分けています。

| 分けたもの | 旧 | 新 |
|---|---|---|
| クラス名 | `LegacySceneDocumentSerializer` | `SceneSerializer` |
| 名前空間 | `ReplayEngine::Scene::Legacy` | `ReplayEngine::Scene::Serialization` |
| ファイル名 | `LegacySceneDocumentSerializer.cpp` | `SceneSerializer.cpp` |
| 保存拡張子 | `.replaystage` | `.replayscene` |

**新 `SceneSerializer` へ SceneDocument 用のオーバーロードは追加していません。**
別クラス・別名前空間・別ファイルなので、曖昧な多重定義は発生しません。

拡張子まで分けたのは、同じ `.replayscene` のままだと v7 リーダーが旧ファイルを開いて
「旧形式のため非対応」と拒否してしまうためです。

### 3-2. 呼び出し側の修正

| ファイル | 修正内容 |
|---|---|
| `framework_scene_document.cpp` | include を Legacy ヘッダへ差し替え。`save_scene_document` / `load_scene_document` を `LegacySceneDocumentSerializer::Save/Load` へ。ファイルダイアログのフィルタとタイトルを「ステージ配置記録」「`.replaystage`」へ変更 |
| `framework_scene_document.cpp` | `create_scene_document` の新規ファイル名を `.replaystage` へ |
| `framework_editor.cpp` | プロジェクトパネルのシーン一覧が列挙する拡張子を `.replaystage` へ。include 追加 |
| `framework.h` | `current_scene_path` の既定を `Main.replaystage` へ。用途をコメントで明記 |

### 3-3. obj 名衝突の再発防止（根本対策）

4 つの構成すべての `ClCompile` へ追加しました。

```xml
<ObjectFileName>$(IntDir)%(RelativeDir)</ObjectFileName>
```

これで `.obj` がソースツリーの構造を保って出力されるため、
**今後どのフォルダに同名 `.cpp` を追加しても衝突しません。**

この対策が要る根拠として、プロジェクトには既に `deferred_renderer.h` が
`Source\render\` と `RePlayEngine\Rendering\Deferred\` の両方に存在しており、
将来 `deferred_renderer.cpp` が追加されれば同じ事故が起きる状態でした。

## 4. PrefabSerializer をどう新形式へ対応させたか

### 旧実装

```cpp
// SceneEntity を 1 件だけ SceneDocument へ入れて旧形式で書き出すだけ
bool PrefabSerializer::Save(const SceneEntity& entity, ...) {
    SceneDocument prefab;
    prefab.Entities().push_back(entity);
    prefab.Entities().front().id = 1;
    return SceneSerializer::Save(prefab, path, error);
}
```

- 保存できるのは `std::optional` でハードコードされた 5 種の Component だけ
- 階層を保存できない（1 件のみ）
- 新しい Component を足しても Prefab には入らない

### 新実装

`RePlayEngine/Scene/Serialization/PrefabSerializer.{h,cpp}`（新規）

```cpp
static bool       Save(const Scene&, Core::ObjectID root, const path&, std::string& error);
static Core::ObjectID Instantiate(Scene&, const path&, std::string& error,
                                  SceneLoadReport* report = nullptr);
```

`SceneData` を経由するため、次がすべて自動で付いてきます。

- Component は**型名で保存し ComponentRegistry で復元**する
- プロパティは **PropertyRegistry の定義に従って**保存・復元する
- **子 GameObject を含む階層**をそのまま保存できる
- 未登録 Component / 未知プロパティは警告してスキップする
- **型ごとの分岐が 1 つも無い。** Component を増やしてもこのファイルは変更不要

そのために `SceneData` へ 2 つの関数を追加しました。

| 関数 | 役割 |
|---|---|
| `CaptureGameObjectSubtree(scene, root, out)` | 起点と子孫だけを抜き出す。起点は必ず親なしにするので、どの階層を保存しても独立した部分木になる |
| `InstantiateSceneData(data, scene, report)` | Scene を消さずに**追加**する。ObjectID は必ず採番し直すので、同じ Prefab を何度置いても衝突しない |

`ApplySceneData`（Scene 読み込み = Clear してから保存 ID のまま復元）とは
役割が違うため別関数にし、Component 生成部分は共通ヘルパ `BuildComponents` へ切り出しました。

呼び出し側 `framework::save_selected_prefab` / `load_prefab` も、
旧 `editor_scene_document` ではなく新しい `object_scene` と `EditorSelection` を見るように
書き換えました。Prefab 配置は `EditorContext` のトランザクション経由なので **Undo できます**。

拡張子は `.replayprefab` のままですが、中身は v7 テキストそのものです。
そのため Prefab をそのまま Scene として開くこともできます。

### 削除したファイル

```
RePlayEngine/Scene/PrefabSerializer.h    → 削除（宣言だけ残す状態は作っていません）
RePlayEngine/Scene/PrefabSerializer.cpp  → 削除
```

## 7. 旧 SceneDocument 経路が残っている理由と廃止予定

### 残した理由

`SceneDocument` は、まだ新 Component へ移行できていない次の情報を保持しています。

| 情報 | 移行先として必要な Component | 現状 |
|---|---|---|
| ステージ素材の配置（AssetGUID + Transform） | `MeshRendererComponent` | 一部移行可能だが、下記と一体で使われている |
| `ShaderLayerStack`（追加シェーダーパスの積み重ね） | `ShaderLayerComponent`（未実装） | 未対応 |
| `CharacterMaterialProfile`（キャラ表現の詳細パラメータ） | `CharacterMaterialComponent`（未実装） | 未対応 |
| クック済み衝突メッシュのパスとセルサイズ | `MeshColliderComponent`（新基盤へ未移植） | 未対応 |

これらを新形式へ移すには、上記 3 つの Component を実装し、
`framework_render.cpp` のステージ描画経路と `MeshCollisionCooker` の接続を組み替える必要があります。
「既存 Player / Stage の Runtime 処理は今回壊さない」という制約と両立しないため、
今回は Legacy として分離するに留めました。

### 二重化していないこと

- **保存経路は用途で分かれており、同じデータを 2 か所へ書いていません。**
  - `.replaystage` … ステージ素材の配置とシェーダー設定（旧）
  - `.replayscene` … GameObject / Component 構成（新・正式）
- **Hierarchy と Inspector からは旧 SceneEntity の UI を既に撤去済み**です。
  旧 SceneDocument へ触れるのはステージ配置ワークスペースと衝突 Cook だけです。

### 廃止予定

```
段階 1  MeshColliderComponent を新基盤へ移植
          → SceneDocument の mesh_collider が不要になる
段階 2  ShaderLayerComponent / CharacterMaterialComponent を実装
          → shader_layers / character_material が不要になる
段階 3  ステージ素材の配置を MeshRendererComponent へ完全移行
          → SceneDocument が保持する情報がゼロになる
段階 4  SceneDocument / LegacySceneDocumentSerializer / UndoStack(旧) /
        framework の scene_entity 系メンバを一括削除
```

段階 1 は次の作業として最も費用対効果が高い箇所です
（`SphereColliderComponent` / `MeshColliderComponent` は既に `IComponent` 派生として
存在しており、新 `Component` を継承させて GameObject 所有へ移すだけで済みます）。
